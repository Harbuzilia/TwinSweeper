## Блок A — корректность определения дубликатов (главный страх пользователя)

**A1 [КРИТИЧНО] Устаревший хэш в кэше подменял SHA-256-верификацию.**
`db_cache.save_file_hash` использовал `COALESCE(excluded.full_hash, file_hashes.full_hash)`:
при записи turbo-хэша для ИЗМЕНЁННОГО файла строка получала новые size/mtime, но
СТАРЫЙ full_hash. Сценарий потери: файл отредактирован «в середине» (размер и
первые/последние 64 КБ те же) → turbo-скан группирует его со старой копией → фаза
полной SHA-256-верификации берёт из кэша устаревший хэш → «дубликат подтверждён» →
уникальный файл предвыделен и удалён. **Это ровно страх пользователя.** Фикс: хэш
валиден только для тех (size, mtime), с которыми вычислен — `CASE WHEN size/mtime
изменились THEN NULL`; turbo-запрос больше не возвращает full_hash. E2E-тест
редактирует середину файла и проверяет, что он НЕ перегруппируется.

**A2 Один физический файл ≠ «дубликаты».** Индексация по `(st_dev, st_ino)`:
хардлинки, junction-алиасы и перекрывающиеся корни скана (C:\ вместе с C:\Users)
больше не дают фантомную пару, удаление «дубликата» в которой уничтожает и
«оригинал» (это один файл). Guard `st_ino != 0` (FAT/exFAT).

**A3 Системный мусор.** `$Recycle.Bin` и `System Volume Information` вырезаются
из каждого обхода: копия в корзине хранит mtime оригинала и иначе стала бы
«оригиналом», помечая живой файл «дубликатом». В directory-junctions не спускаемся
(двойной обход / бесконечный цикл).

**A4 «В корзину» без send2trash.** `use_trash=True` при недоступной библиотеке
теперь ОТКАЗЫВАЕТ (ошибка + пропуск), а не молча делает `os.remove` — нарушение
H5 устранено и для этого случая; чекбокс корзины дизейблится.

**A5 Сканы без проверки содержимого.** Группировка только по размеру/имени
(содержимое не сравнивалось) больше НЕ предвыделяет файлы к удалению и показывает
предупреждающий баннер.

**A6 Журнал при отмене.** `perform_delete/hardlink/move` пишут журнал в `finally`:
отмена середины операции больше не теряет undo для уже обработанных файлов.

**A7 TypeError в настройках.** `get_styled_dialog` без обязательного `content`
ронял «Очистить кэш» и «Контекстное меню» после выполнения реальной работы.

**A8 scan_for_sample** исключает алиасы образца по inode, а не только по точному пути.

## Блок B — корректность деструктивных операций

- **B9** Клинер сверяет каждый файл со снимком скана (C2) перед удалением — путь,
  занятый реальным изменившимся файлом, пропускается. `verify_file_unchanged`
  перенесён в scanner.py (общий, без циклического импорта).
- **B10** «Переместить» тоже вызывает `_protect_originals` — группа не уезжает целиком.
- **B11/B3** `perform_move`: same-volume — атомарный `os.replace` (без окна
  копирования); cross-volume — копия проверяется, источник удаляется только после
  неё, при сбое удаления источника копия откатывается (невидимый дубль невозможен);
  имя резервируется через `O_CREAT|O_EXCL` (TOCTOU перезаписи закрыт).
- **B12** undo: файловые операции ВЫНЕ блокировки (вкладка «История» не фризит);
  `undone=True` только при полном успехе — частичный сбой остаётся повторимым.
- **B13** hardlink: краш между rename восстанавливает orphaned-backup при повторе;
  уже-слинкованная пара не журналируется (undo не разъединит чужие линки).
- **B14** `load_history` валидирует тип — битый scan_history.json не роняет скан-воркер.

## Блок C — качество результатов и UX

- **pHash complete-linkage**: компонента связности разбивается так, что ВСЕ пары
  внутри финальной группы в пределах порога — цепочки A~B~C больше не сливают
  непохожие фото. `.avif` поддержан (Pillow 12.3). Отчёт о неподдерживаемых
  форматах выводится ДО early-return (HEIC-библиотека не молчит).
- **Клинер**: `.bak/.dmp/.old` и файлы >100 МБ не предвыделяются (осознанные данные);
  битые ярлыки — пропуск при недоступном диске цели; декодирование .lnk выбирает
  вариант, при котором путь существует (mbcs→utf-8), без lossy-фабрикации путей.
- **exclude с разделителями** (`D:\Games`) матчится как префикс пути, а не игнорится.
- `status_icon.name`→`.icon` (flet 0.86 — иконка ошибки не менялась); compare
  busy-guard; set_mode блокируется во время скана; run-generation защита от
  затирания UI нового скана колбэками старого; контекстное меню остаётся в
  настройках; trash_default «живой»; невалидный min size подсвечивается;
  0-байтные группы не предвыделяются; уникальное имя tmp миниатюр.

## Блок D — длинные пути >260

`scanner.long_path()` добавляет префикс `\\?\` ТОЛЬКО для путей длиннее MAX_PATH
(обычные пути не меняются байт-в-байт — ноль риска). Применён к листовым операциям
чтения (хэши, byte-compare, dHash) — глубокие файлы хэшируются. К деструктивным
операциям НЕ применяется: они сохраняют обычный путь, поэтому C2-проверка на
>260-цели безопасно отказывает и файл пропускается. Корни `os.walk` не
префиксуются, чтобы не сломать relpath/normcase/exclude.

## Вердикт по безопасности (раунд 3)

**Может ли программа теперь при обычном использовании (скан всего диска → удалить
выбранное в корзину) удалить НЕ-дубликат? — НЕТ.** Все три цепочки, пробивавшие
защиту в раунде 2, закрыты:
1. устаревший кэш больше не подменяет SHA-256-верификацию (A1);
2. копия из корзины / системный файл не становится «оригиналом» (A3);
3. один физический файл (хардлинк/junction/перекрывающийся корень) не считается
   дубликатом сам себя (A2).
Плюс: «в корзину» без библиотеки не превращается в безвозвратное удаление (A4),
сканы без проверки содержимого не предвыделяются (A5), отмена не теряет журнал (A6).

## Что осталось (честно, не закрыто в раунде 3)

- **Полный обход деревьев >260 символов**: префикс применён к операциям чтения,
  но сам `os.walk` по корню >260 зависит от системной настройки `LongPathsEnabled`
  / манифеста приложения. Требует manifest `longPathAware` в PyInstaller-сборке —
  операционная задача, не чисто кодовая. Деструктивные операции на таких путях
  безопасно отказывают.
- **Миллисекундное TOCTOU-окно** между C2-проверкой и `os.remove`/`send2trash`
  неустранимо без файловых блокировок на уровне ОС (для однопользовательского
  десктопа риск пренебрежим; C2 сужает окно до миллисекунд).
- **BK-tree/LSH для pHash**: complete-linkage закрывает пользовательский риск
  (непохожие фото не в одной группе), но кластеризация остаётся O(n²) — для
  библиотек 100k+ изображений нужен индекс. Не критично для целевого масштаба.
- **Пагинация результатов** после удаления сбрасывается в начало (косметика,
  намеренно не трогали — риск регрессии выше пользы).
- **mypy/типизация**, планировщик фоновых сканов, дедуп медиа по метаданным —
  вне профиля продукта (см. анализ продуктового агента раунда 2).

## Часть 1. Исправленные проблемы

### Критические (риск потери данных)

**C1 — Хардлинк визуально похожих фото терял контент.**
`hardlink_manager.py` / `ui/results_view.py`.
Результаты поиска похожих изображений (pHash) открывались в том же экране результатов
с активной кнопкой хардлинка, а `replace_with_hardlink` не проверял байтовую
идентичность: похожая (но другая!) фотография заменялась ссылкой на оригинал —
безвозвратно.
*Фикс (двухслойный):* (1) `ResultsView` получил флаг `allow_hardlink=False` для
pHash-результатов — кнопка скрыта; (2) в `replace_with_hardlink` перед заменой
обязательная проверка: совпадение размера **и** полного SHA-256, иначе отказ
с объяснением. *Тесты:* `tests/test_hardlink_manager.py` (отказ при разных
размерах/контенте), `tests/test_results_view.py` `TestHardlinkVisibility`.

### Высокие

**H1 — Вкладка «Общие файлы» падала с KeyError.**
`ui/compare_view.py` / `scanner.py`.
`compare_folders` возвращает ключи `file_a/file_b/similarity/newer/larger`, а вью
читал `name/path_a/path_b/size` — сравнение папок в UI валилось.
*Фикс:* вью приведён к реальной схеме (бейджи «новее»/«больше» уже были в данных).
*Тесты:* тесты схемы `compare_folders` в `tests/test_scanner.py`.

**H2 — Fallback при ошибке сравнения имел несовместимую схему.**
`main.py`.
При ошибке сравнения папок возвращалась структура с чужими ключами → KeyError,
поток умирал, прогресс висел.
*Фикс:* `EMPTY_COMPARE_RESULT` — зеркало реальной схемы
(`unique_a/unique_b/common/total_files`); ошибка показывается в UI.
*Тесты:* `tests/test_main.py` `TestCompareFallbackSchema` (ключи и пустота значений).

**H3 — Фоновые воркеры теряли контекст страницы.**
`main.py`.
Воркеры запускались через «сырой» `threading.Thread` без контекста flet — обращения
к `page`/диалогам из потока ненадёжны (след отладки `_probe_fp.py` это подтверждал).
*Фикс:* все 5 воркеров сканирования/удаления/хардлинка/отмены и undo переведены на
`page.run_thread(...)`, который в flet 0.86.5 восстанавливает контекст страницы.
*Тесты:* headless-тесты вью (`tests/test_sweeper_view.py` и др.) + import-smoke.

**H4 — «Очистка мусора» удаляла навсегда без подтверждения.**
`ui/sweeper_view.py` / `sweeper.py`.
Клик по «Очистить» сразу безвозвратно удалял файлы; `desktop.ini` считался мусором
(это легитимный файл настройки папок Windows).
*Фикс:* диалог подтверждения (количество, иконка, красная кнопка), опция
**«в корзину»** (по умолчанию включена, для файловых режимов); пустые папки удаляются
только `os.rmdir` (физически не может удалить непустую); операция журналируется в
`operations_log.json`; не удалённое остаётся в списке для повтора; `desktop.ini`
убран из `JUNK_FILENAMES` (sweeper.py:9). *Тесты:* `tests/test_sweeper_view.py`
`TestConfirmationDialog`, `TestEmptyFolderDeletion`.

**H5 — Сбой корзины молча превращался в безвозвратное удаление.**
`main.py` (delete_files_handler) / `ui/sweeper_view.py` (execute_clean).
Если `send2trash` падал, код переходил к `os.remove` — файл терялся навсегда вместо
того, чтобы остаться.
*Фикс:* при сбое корзины файл **не удаляется**, ошибка пишется в список и показывается
пользователю; fallback на `os.remove` отсутствует физически.
*Тесты:* `tests/test_sweeper_view.py` `test_failed_trash_keeps_file`.
